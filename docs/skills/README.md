# Research Harness Skills

This directory documents the **skill subsystem** — how Research Harness ships
reusable Skill packages and how any agent platform can consume them without
RH having to know about the agent in advance.

## What is a skill?

A skill is a folder under [`skills/`](../../skills/) that contains a
`SKILL.md` file with a YAML front-matter header (the format used by Claude
Code and Codex). The body is free-form Markdown — instructions, reference
material, templates — that an agent reads when the user's intent matches the
skill's natural-language triggers.

Skills are vendor-neutral. The same `SKILL.md` is consumed by Claude Code,
Codex, Gemini CLI, OpenCode, and any future agent that understands the
format.

## Architecture

```
RH repo
├── skills/                   single source of truth
│   ├── manifest.json         machine-readable index (regenerated by `rh skill index`)
│   ├── paper-writing/        ← one folder per skill
│   │   ├── SKILL.md
│   │   └── tracks/...
│   ├── final-bundle-quality/ ← promoted v2 package example
│   │   ├── SKILL.md
│   │   ├── skill.yaml
│   │   └── contracts/
│   │       ├── input.yaml
│   │       ├── output.yaml
│   │       └── guardrails.yaml
│   └── agent-profiles/       templates for `.rh-agent.toml`
│       ├── claude-code.toml
│       ├── codex.toml
│       ├── gemini.toml
│       ├── opencode.toml
│       └── ... additional templates as needed
└── packages/research_harness/.../skill/   CLI + library
```

Three layers, each independent:

1. **Source** — the `skills/` directory plus its generated `manifest.json`.
   No agent-specific assumptions. This surface is reserved for user-facing
   research workflows. `SKILL.md` is the minimum portable surface; promoted RH
   skills may also include `skill.yaml` plus `contracts/` for runtime
   validation, replay tests, and promotion policy. Every public `SKILL.md`
   also carries a lightweight product contract in front matter:
   `public_suite`, `task_type`, `data_access_level`, `inputs`, `outputs`,
   `gates`, `artifact_schemas`, and `estimated_runtime`. These fields are
   copied into manifest `extras` and validated by `scripts/codex_skill_manifest_check.py`.
2. **Agent self-declaration** — every consuming agent ships its own
   `.rh-agent.toml` declaring `install_path`, `format`, and `strategy`. RH
   reads this file and obeys it. RH does not maintain a list of supported
   agents.
3. **Delivery** — three strategies are supported:
    - `symlink` (default): each skill folder is symlinked into the agent's
      install path. Updates flow automatically.
    - `copy`: a recursive copy. Used when the agent's loader doesn't follow
      symlinks, or in CI / sandboxes.
    - `mcp-runtime`: nothing is written to disk; the agent calls the MCP
      tools `skill_list` and `skill_get` at runtime instead.

Promoted v2 packages add a fourth runtime-facing layer without replacing the
portable skill surface:

4. **Runtime contract** — `skill.yaml` is converted into a
   `CapabilityManifest` and `RunSpec`. Auto-runner checkpoints may reference a
   skill by name, and callable evaluators such as `final-bundle-quality` execute
   through `research_harness.evaluator.runtime` after capability/tool/artifact
   guardrails pass. Evaluator runners live under
   `research_harness.evaluator.runtime`. The declared output, sidecar `run_trace`, and
   `runtime_trace_grade` are typed artifacts recorded through the orchestrator,
   not ad hoc files.

## Quick start

```bash
# 1. Build the manifest (setup.sh does this automatically).
rh skill index

# Optional: inspect promoted v2 packages as runtime capabilities.
rh skill capabilities

# 2. Install for whichever agent you're using.
rh skill install --agent claude-code      # uses skills/agent-profiles/claude-code.toml
rh skill install --agent opencode
rh skill install --agent gemini
rh skill install --target ~/.claude/skills  # ad-hoc, no profile
rh skill install                           # auto: looks for ./.rh-agent.toml

# 3. Verify what's installed.
rh skill verify --agent claude-code

# Optional: inspect task-first public suites.
rh skill list --group-by-suite
rh skill list --suite paper
```

## LG10 Productization Boundary Preview

The skills/docs boundary preview documents the LG10 public-productization gate
without changing any skill runtime, manifest generation, MCP runtime delivery,
or default agent routing behavior.

- Boundary id: `lg10-public-productization-boundary`.
- Payload schema: `lg10_productization_boundary.v1`.
- Allowed future pattern: `one_public_surface_per_gate_slice`.
- Every future public-surface implementation must be opt-in,
  backwards-compatible by default, shape-locked, documented, and separately
  verified.
- LG8/LG9 evidence is a prerequisite, not approval to productize.

Current opt-in boundary previews cover CLI, MCP, HTTP, and Python facade. This
skills/docs boundary preview records the same policy for agents and skill
authors; it does not add a new public skill, does not auto-route user requests
to LG10 productization, does not publish a Zotero integration, and does not change doctor or showcase behavior.
